# AI Travel Planning and Booking Agent — Design Specification

**Status:** Approved for implementation planning
**Version:** 1.0 (V1 scope)

## 1. Problem Statement

Manually planning a multi-leg trip — comparing flights and hotels across sites, building a
day-by-day itinerary, and filling in booking forms — is tedious. This project builds an AI
agent that automates search, comparison, and itinerary planning end-to-end, while keeping the
one irreversible/financial step (payment) strictly under human control.

This is a capstone/portfolio project. It is intended to demonstrate, end to end and for real:

- LLM orchestration with LangGraph, including structural (not just prompted) safety gates.
- Tool use via MCP across four distinct integrations (travel search, browser automation,
  email, CRM).
- Production-style deployment: self-managed Kubernetes on AWS, Terraform + Packer, GitOps,
  CI/CD, and observability.

## 2. Goals

- A full working demo: a user states trip constraints in conversation → receives ranked
  flight/hotel options (including multi-leg trips) → receives a personalized itinerary →
  picks options → the agent fills a mock booking form via browser automation → the flow stops
  for **explicit human approval** → a confirmation email is sent → the trip is logged to a CRM.
- A structurally safe human-in-the-loop pattern for an agent operating adjacent to a
  payment-shaped flow, where safety is enforced by graph topology and site design, not by
  trusting model behavior.
- Real infrastructure: a self-managed Kubernetes cluster on AWS EC2 (kubeadm), provisioned by
  Terraform and Packer, deployed via GitOps (Argo CD), observed via Prometheus/Grafana, built
  and shipped via CI/CD.

## 3. Non-Goals (V1)

- No real payment processing or credit-card handling — ever, not in a later phase either. The
  mock booking site has no payment field or endpoint in its codebase at all.
- No real booking-website integration (no partner/site has been selected; mock site only).
- No multi-user accounts or authentication — single demo user per session, consistent with the
  author's prior YOLO-style project.
- No mobile app; no scale/concurrency optimization.
- No dedicated points-of-interest/attractions API — itinerary content is generated by the LLM
  from its own knowledge, not sourced from a separate places API.
- No highly-available control plane (single control-plane node; documented limitation, see
  Section 10).

## 4. Architecture Overview

### 4.1 Components

| Component | Role |
|---|---|
| React chat frontend | Conversational UI for trip input, option selection, and the pre-submit review screen. Talks to backend over REST + SSE/WebSocket for streamed agent responses. |
| FastAPI backend | Hosts the LangGraph agent graph; exposes endpoints for starting a conversation, sending messages, submitting selections, and approving/rejecting the booking-review gate. |
| LangGraph StateGraph | The orchestrator: fixed nodes, conditional edges, `interrupt()`-based human gates. |
| Postgres | LangGraph checkpointer (conversation/graph state) **plus** application tables (trip requests, search results, traveler details, booking status). System of record. |
| Amadeus MCP server (custom) | `search_flights`, `search_hotels` tools wrapping the Amadeus self-service API (sandbox environment). |
| Playwright MCP server (Microsoft, self-built & pinned) | Browser automation to fill the mock booking site. No database or secret access. |
| Gmail MCP server (custom) | `send_email` tool (OAuth2) for the final itinerary/confirmation email. |
| HubSpot MCP server (custom) | `upsert_contact`, `create_trip_record` tools writing to HubSpot CRM (free tier). |
| Mock booking site | Small separate web app simulating an airline/hotel booking form (traveler details, seat/room extras). Ends at a "Proceed to Payment" screen; **no payment UI or endpoint exists anywhere in this app**. |
| Claude (Anthropic API) | Powers NL understanding, option ranking narration, and itinerary generation. |

All four external integrations (search, browser automation, email, CRM) are exposed through
MCP servers, for architectural consistency: every external system sits behind the same
tool-call boundary, making each integration independently testable/mockable, and keeping
LangGraph node code uniform.

### 4.2 High-Level Flow

```
User (React chat) ⇄ FastAPI ⇄ LangGraph agent ⇄ [Amadeus MCP, Playwright MCP, Gmail MCP, HubSpot MCP]
                                     │
                                 Postgres (state + app data)
```

## 5. LangGraph Workflow

### 5.1 Orchestration Approach

The workflow is modeled as an explicit LangGraph `StateGraph` with one node per step and
mostly-deterministic edges (conditional edges for retries/no-results). This was chosen over a
multi-agent supervisor pattern or a freeform ReAct agent with all tools available, because the
hard requirement — payment/booking submission must never happen without human sign-off —
needs to be guaranteed by the code path, not by trusting an LLM's judgment. With a fixed graph,
the human-review step is structurally required to proceed; with a freeform agent, nothing
prevents the model from choosing to skip it.

### 5.2 Nodes (in order)

1. **`collect_trip_request`** — Gathers origin, destination(s) (list, supporting multi-leg
   trips), dates, budget, traveler count, and preferences via conversation; validates against a
   Pydantic schema; loops back on missing/invalid fields.
2. **`search_flights_and_hotels`** — Calls Amadeus MCP tools (parallel flight + hotel search per
   leg). Full results are written to application tables (not graph state) to avoid checkpoint
   bloat; graph state holds result IDs and, optionally, a small shortlist. Empty results route
   to a `no_results` branch that asks the user to relax constraints rather than dead-ending.
3. **`recommend_options`** — Ranks/filters to a shortlist (top 3–5 per leg) within budget.
   Numeric/factual fields (price, times, stops) are rendered directly from typed data; the LLM
   only narrates around fixed facts, so it cannot misrepresent them.
4. **`generate_itinerary`** — LLM builds a preliminary day-by-day itinerary from destination(s),
   dates, and preferences, before a specific flight/hotel is chosen.
5. **`await_selection`** *(interrupt)* — Pauses for the user to pick a flight + hotel per leg
   from the shortlist. Resumes on frontend submission.
6. **`finalize_itinerary`** — Regenerates/adjusts the itinerary to incorporate the actual
   selected flight times and hotel locations.
7. **`collect_traveler_details`** — Gathers per-traveler details required by the mock site's
   form. Writes to a dedicated, encrypted `traveler_details` Postgres table; graph state holds
   only a `traveler_details_id` foreign key, never the raw values (see Section 6.1).
8. **`fill_booking_form`** — The **backend node** (not the Playwright MCP server) fetches and
   decrypts the traveler record just-in-time, then passes the required plaintext values to the
   Playwright MCP tool call in memory only. Playwright fills the mock site's form and stops at
   the page showing a filled summary immediately before the "Proceed to Payment" button.
   Passport/ID number and DOB fields are masked before a review screenshot is captured.
9. **`human_review_gate`** *(interrupt)* — Presents the masked filled-form summary/screenshot in
   the review UI. Waits for explicit **Approve** or **Reject**. This gate approves the filled
   mock form and the downstream notification/CRM actions — **not a real booking or payment**,
   neither of which exist in this system. Reject routes back to `collect_traveler_details` or
   `await_selection` depending on the stated reason.
10. **`send_confirmation_email`** — On approval, Gmail MCP sends the final itinerary + trip
    summary (not a payment receipt — none exists). Carries an idempotency key so retries can't
    double-send.
11. **`update_crm`** — HubSpot MCP upserts the contact and creates a trip/deal record. Also
    carries an idempotency key so retries can't create duplicate records.
12. **`end`** — Terminal state; conversation summary shown to user.

Each MCP-tool-calling node (2, 8, 10, 11) has a bounded-retry edge (3 attempts, exponential
backoff) before routing to an `agent_error` node that surfaces a plain-language failure to the
user. `fill_booking_form` failures do not retry blindly — they route to a dedicated failure
state with an explicit retry/abort choice, since silently retrying a form-fill is riskier than
retrying a search.

### 5.3 State Schema (top-level fields)

`trip_request`, `flight_result_ids` / shortlist, `hotel_result_ids` / shortlist, `itinerary`,
`selected_flights`, `selected_hotels`, `traveler_details_id` (FK, not raw data),
`booking_form_result`, `approval_status`, `email_status` (with idempotency key),
`crm_status` (with idempotency key), `retry_counts`, `error_log`.

`error_log` is explicitly typed as sanitized `{code, message}` pairs only — never traveler PII,
OAuth tokens, API keys, or raw third-party responses.

## 6. Data & Security

### 6.1 Sensitive Data Handling

LangGraph's Postgres checkpointer persists a snapshot of the full graph state after every
node, across multiple checkpoint rows (one per superstep). This means sensitive fields placed
directly on graph state would be written into Postgres multiple times, not avoided by being
"only in state." The design instead is:

- Traveler details (including passport/ID) are written to a dedicated `traveler_details`
  table, not onto the graph state object.
- Sensitive columns (passport/ID number, DOB) are encrypted at the application layer (AES-GCM,
  key sourced from AWS Secrets Manager/KMS — never a plaintext env var) before insert.
- Graph state carries only a `traveler_details_id` foreign key.
- The `fill_booking_form` backend node fetches and decrypts just-in-time, holds plaintext in
  memory only for the duration of the Playwright MCP call, and never writes it back onto graph
  state. It is excluded from logs, traces, metrics, and error messages.
- Playwright MCP receives plaintext values as call arguments only; it has no database or
  encryption-key access, must not persist values in browser storage/cookies, and must not leak
  them into returned DOM snapshots.
- Review screenshots mask passport/ID and DOB fields before capture/storage.
- Retention policy: traveler PII rows are purged on a defined schedule (e.g. N days after the
  session, or immediately after the confirmation email sends) — data minimization, not just
  encryption at rest.
- Explicit operational rule: **only synthetic/fake passport data should ever be entered** —
  this is a demo against a mock site, never a real travel document.

### 6.2 Secrets Management

- All secrets (Amadeus API key, Gmail OAuth client/token, HubSpot API key, DB encryption key,
  Postgres credentials) live in Kubernetes Secrets, created at runtime by the **External
  Secrets Operator** from **AWS Secrets Manager**.
- Argo CD's GitOps repository contains only `ExternalSecret` reference objects — never secret
  values.
- Each MCP server receives only the credentials it needs (e.g. Playwright MCP gets zero
  secrets or DB access; Gmail MCP gets only the Gmail token) — least privilege between tools.

### 6.3 Network Security

Kubernetes namespaces alone do not provide network isolation, so explicit `NetworkPolicy`
resources are required:

- Frontend → backend only.
- Backend → {Amadeus MCP, Playwright MCP, Gmail MCP, HubSpot MCP, Postgres}.
- Playwright MCP → mock booking site only (no egress to Postgres or secrets).
- Postgres accepts ingress from the backend only.
- Every MCP server has a default-deny policy with only its required ingress/egress explicitly
  opened.

### 6.4 Prompt Injection

Fixed LangGraph routing (Section 5.1) means untrusted input cannot cause the agent to invoke
tools out of order or skip the review gate — but this does not fully remove prompt-injection
risk, since untrusted text can still influence LLM-generated summaries and tool call
*arguments* within a node. Mitigations:

- Every MCP tool's inputs and outputs are validated against strict typed schemas
  (length limits, enums where applicable, allowlists — e.g. only known IATA airport codes).
- Numeric/factual data shown to the user is rendered from typed fields, not LLM free text
  (Section 5.2, node 3).
- This is defense-in-depth, not a full mitigation, and is documented as a residual risk
  (Section 10).

### 6.5 Mock Site Safety

The mock booking site has no payment form field or payment endpoint anywhere in its codebase —
this is a structural absence, not a policy the agent is trusted to follow. Playwright cannot
navigate beyond the review screen because no route or control exists to do so.

## 7. Error Handling

- Every MCP tool call is wrapped with typed exceptions (e.g. `AmadeusRateLimitError`,
  `PlaywrightTimeoutError`, `GmailSendError`) mapped to sanitized `error_log` codes.
- Bounded retries (3x, exponential backoff) for transient failures (rate limits, timeouts) on
  search, email, and CRM nodes.
- `fill_booking_form` failures route to a dedicated failure state with an explicit retry/abort
  choice rather than retrying automatically.
- Partial-failure handling post-approval: if email succeeds but CRM fails (or vice versa), the
  graph does not roll back the approval — it marks that specific step failed in state and
  offers a retry, since the human already approved the booking itself; email/CRM are downstream
  side effects, not the approval itself.
- Idempotency keys on `send_confirmation_email` and `update_crm` (derived from the trip/session
  ID) prevent duplicate sends/records if a retry follows a crash that happened *after* the side
  effect succeeded but *before* its status was persisted.
- All errors are surfaced to the user in plain language via the chat UI — never raw stack
  traces or upstream API payloads.

## 8. Infrastructure, CI/CD, GitOps, Observability

### 8.1 Provisioning

- **Terraform** provisions AWS networking (VPC, subnets, security groups) and EC2 instances for
  a self-managed Kubernetes cluster (1 control-plane node + N worker nodes). Remote state uses
  an S3 backend with native locking (`use_lockfile = true`, Terraform ≥1.10) — no DynamoDB lock
  table (DynamoDB-based locking is deprecated).
- **Packer** builds a reusable Kubernetes node AMI (kubeadm, kubelet, container runtime
  pre-installed).
- The control-plane node initializes via EC2 `user_data` running `kubeadm init`. Worker nodes
  retrieve a short-lived `kubeadm join` command from **AWS SSM Parameter Store** at boot.
  Terraform `remote-exec` is deliberately avoided.
- The control plane is a **single node for this demo — not highly available**. This is an
  accepted, explicitly documented limitation, not a hidden gap. The bootstrap design (SSM-based
  join flow, AMI-based node provisioning) is intended to extend to a stacked or external-etcd
  multi-control-plane setup in a future phase without a redesign.

### 8.2 Repository Layout

Monorepo, with a clearly separated infra/deployment tree:

```
/infra   — Terraform + Packer
/k8s     — Kustomize base + overlays/dev, overlays/prod
/backend, /frontend, /mcp-servers/*, /mock-booking-site — application code
```

No second GitOps repository — kept in the same repo for a project this size.

### 8.3 Container Images

Frontend, backend, mock-booking-site, and each custom MCP server (Amadeus, Gmail, HubSpot) are
separate Dockerfiles/images. The Playwright MCP server image is **built from Microsoft's
official Playwright MCP source, pinned to a specific version/commit** — never an unpinned
`latest` tag.

### 8.4 CI/CD and GitOps Separation

- GitHub Actions: lint/type-check → unit tests → build images → push to a registry (e.g. ECR).
  Once all required builds and tests succeed, the pipeline's only cluster-facing action is
  updating the relevant image tag in the appropriate `k8s/overlays/*` manifest.
- **Argo CD is the sole component that applies manifests to the cluster.** CI never applies
  directly.

### 8.5 Observability

- Prometheus scrapes the backend (FastAPI instrumentation), Postgres (`postgres_exporter`), and
  cluster/node metrics (`node-exporter`, `kube-state-metrics`).
- **Application-level metrics** (separate from infra metrics): workflow completions, workflow
  failures, interrupt counts (per gate), retry counts (per node), per-node duration, MCP tool
  call latency (per server), and downstream side-effect status (email/CRM success/failure).
  **Metrics and traces must never contain traveler PII** — the same sanitization boundary as
  `error_log`.
- Grafana dashboards for request latency/error rate, graph-node duration, MCP tool success/
  failure rates, and cluster health. Lightweight Alertmanager rules for high error rate or
  booking-flow node failures.

## 9. Testing Strategy

- **Unit tests**: Pydantic schema validation, ranking/filtering logic, itinerary-assembly
  logic, idempotency-key generation, encryption/decryption helpers (test key only).
- **Node-level tests**: each LangGraph node tested in isolation with mocked MCP tool responses
  (success, empty-result, error, timeout) to verify state transitions and routing.
- **MCP server tests**: each custom MCP server (Amadeus, Gmail, HubSpot) tested against
  recorded/mocked upstream responses so the default suite doesn't depend on live third-party
  APIs or quotas; contract tests confirm malformed/oversized/non-allowlisted inputs are
  rejected. **Live sandbox integration tests are a separate job** — run manually, on a
  schedule, or gated on required secrets being present — keeping normal CI deterministic.
- **LangGraph persistence tests**: for both `interrupt()` gates (`await_selection`,
  `human_review_gate`) — checkpoint creation, resume behavior after a simulated process
  restart, correct Approve/Reject routing, and prevention of duplicated downstream actions on
  resume.
- **Crash-recovery tests**: a side effect (email/CRM) succeeds but the process crashes before
  its status is persisted; on resume, the idempotency key must prevent a duplicate email or
  duplicate CRM record.
- **PII-leak tests**: known synthetic PII fixture values are asserted to never appear —
  verbatim, not just via pattern match — in checkpoints, logs, metrics, traces, screenshots,
  browser storage, or MCP responses. Pattern matching (e.g. passport-shaped strings) is an
  additional safeguard, not the primary check.
- **Postgres tests**: migrations from an empty database, foreign-key constraints, encrypted-
  column round-trip correctness, and retention/purge job behavior.
- **Playwright/mock-site tests**: component tests for the mock site's form validation; a
  Playwright suite runs the fill flow headless in CI against a running instance, asserting the
  flow stops at the pre-payment screen, that masked screenshots contain no raw PII, and that
  **no route or control exists to navigate past the review screen** (there is no payment field
  or endpoint to reach in the first place).
- **Security tests**: NetworkPolicy assertions (e.g. verifying Playwright MCP cannot reach
  Postgres).
- **Infra tests**: `terraform validate`/`plan` in CI on every infra PR; `kustomize build`
  dry-run for both overlays. `kind`-based smoke tests validate Kubernetes manifests and
  in-cluster service communication only — **AWS-specific behavior (IAM, EBS, External Secrets
  Operator ↔ Secrets Manager integration) requires verification in the real AWS dev
  environment**, not `kind`.

## 10. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| LLM-generated summaries subtly misrepresent search results (e.g. wrong price shown) | Numeric/factual data is rendered from typed fields directly; LLM only narrates around fixed facts. |
| Prompt injection via user input or upstream API text influencing generated summaries or tool arguments | Fixed LangGraph routing prevents out-of-order tool invocation or gate-skipping; typed schemas, length limits, and allowlists validate every MCP tool's inputs and outputs as defense-in-depth. |
| Third-party service outage (Amadeus, Gmail, or HubSpot down or rate-limited) | Bounded retries with backoff, graceful degradation (e.g. surfacing a clear "try again later" rather than hanging), and checkpoint-based recovery so a resumed session doesn't restart the whole conversation. |
| Amadeus sandbox data is unrealistic or sparse | Documented known limitation; `no_results` handling designed regardless. |
| Mock site drift breaks Playwright selectors | Mock site and its Playwright automation are versioned together in the same repo; site changes require updating the automation/tests in the same PR. |
| Single control-plane node is a single point of failure | Explicitly documented as acceptable for a demo (Section 8.1); not a hidden gap. |
| Scope creep across many subsystems risks an unfinished demo | Explicit phased roadmap below — a thin vertical slice ships before infra polish. |
| kubeadm/Packer/SSM bootstrap complexity is nontrivial | More infra work than managed EKS; budgeted as its own milestone, with a `kind`-cluster fallback if it stalls. |

### Alternatives Considered

- **Multi-agent supervisor** or **freeform ReAct agent** orchestration — rejected in favor of
  an explicit LangGraph StateGraph, for a stronger structural safety guarantee around the
  human-review gate.
- **Managed EKS** or a **cheap single-VM k3s** cluster — rejected in favor of self-managed
  kubeadm on EC2, per the author's explicit choice, for greater educational depth.
- **Airtable + SendGrid** or **HubSpot + SendGrid** — rejected in favor of **Gmail API +
  HubSpot**.
- **Custom MCP servers for every integration** — rejected in favor of reusing the official
  Playwright MCP server (pinned build) rather than reimplementing browser automation.

## 11. Roadmap (Implementation Phases)

1. **Local development — core agent logic.** LangGraph agent + mocked MCP tools + Postgres,
   no infra. Proves the workflow logic, both `interrupt()` gates, and retry/error handling work
   correctly in isolation.
2. **Local development — real integrations.** Real MCP servers (Amadeus, Gmail, HubSpot,
   Playwright) wired in against sandboxes; mock booking site built and automated end-to-end.
   Still running locally/Docker Compose.
3. **Infrastructure provisioning.** Terraform + Packer build the AMI and AWS networking;
   kubeadm cluster stood up (control plane via `user_data`, workers via SSM join); NetworkPolicies
   and External Secrets Operator wired in.
4. **Kubernetes deployment.** All application services deployed to the cluster via Kustomize
   overlays (`dev` first), manually applied to validate manifests before GitOps takes over.
5. **CI/CD and GitOps.** GitHub Actions pipeline (lint/test/build/tag-bump) wired to Argo CD,
   which becomes the sole applier of manifests from that point forward.
6. **Observability.** Prometheus/Grafana deployed; application-level metrics instrumented;
   dashboards and lightweight alerting rules built out.
7. **Production Validation / Demo.** Full end-to-end verification of the complete workflow
   running on the real AWS Kubernetes environment (`prod` overlay) — happy path and reject-at-
   review-gate path — with monitoring dashboards and alerts confirmed to reflect live activity
   during the run.
