# AI Travel Planning and Booking Agent Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build an AI travel agent that plans and books a multi-leg trip end to end — searches flights/hotels, builds an itinerary, fills a mock booking form, stops for human approval, emails the confirmation, and logs the trip to a CRM.

**Architecture:** A React chat frontend talks to a FastAPI backend hosting a LangGraph agent. The agent calls four MCP servers (Amadeus for search, Playwright for browser automation, Gmail for email, HubSpot for CRM). Persistence is environment-based behind two abstraction interfaces — a checkpoint-storage interface (LangGraph's own `BaseCheckpointSaver`) and an application-repository interface — so the graph and business logic never depend on a concrete database. Local development and tests run entirely on SQLite (both interfaces); production swaps in DynamoDB for checkpoints and PostgreSQL for application data, with no changes to node or repository-calling code. The stack deploys to a self-managed Kubernetes cluster on AWS EC2 via Terraform/Packer, with Argo CD GitOps and Prometheus/Grafana observability.

**Tech Stack:** Python, FastAPI, LangGraph, `langgraph-checkpoint-sqlite`, MCP, Anthropic Claude, React, SQLite (dev/test), PostgreSQL + SQLAlchemy/Alembic (prod app data), DynamoDB + boto3 (prod checkpointer), Docker, Kubernetes on AWS EC2 (kubeadm), Terraform, Packer, Argo CD, Prometheus, Grafana, GitHub Actions.

## Global Constraints

- The LangGraph workflow and all business logic depend only on the checkpoint-storage interface (`BaseCheckpointSaver`) and the application-repository interface — never on SQLite, Postgres, or DynamoDB directly. Concrete adapters are selected by a factory based on environment configuration.
- Traveler PII (passport/ID, DOB) is never stored on LangGraph graph state — only a `traveler_details_id` reference, resolved through the application repository to an encrypted row/item.
- The LLM must not invent numeric facts (price, time, rating) — those come from typed tool results, never regenerated by the model.
- The agent must never fill or submit payment information. The mock booking site has no payment field or endpoint at all.
- The booking must always stop for explicit human approval before any email/CRM side effect runs.
- Every MCP/LLM call retries with backoff before routing to a graceful error node, except the booking-form fill, which never retries automatically.
- Email and CRM writes are idempotent — a retry after a crash must never duplicate them, regardless of which repository adapter is active.
- The final deployment must use self-managed Kubernetes on AWS EC2 via kubeadm, not EKS.
- Dev and prod are separated by Kubernetes namespaces and Kustomize overlays; the production DynamoDB checkpoint table is separated per environment (table-per-environment or a shared table with an `env#` partition-key prefix — decide in Checkpoint 23c).
- All AWS resources are provisioned with Terraform; the node image is built with Packer.
- Automated tests must include: SQLite-based unit/local tests (default, no external services), node-level tests against fakes, real MCP transport integration tests, and separate Postgres/DynamoDB integration tests for the production adapters.

## First Milestone To Build

Do not start with MCP servers, infrastructure, or the frontend. Start with this local proof,
running against fakes and local SQLite only (no containers, no cloud):

```text
user message -> collect_trip_request -> search -> recommend -> itinerary
             -> select -> traveler details -> fill booking form -> human review
             -> email + CRM
```

Checkpoints 2-14 build exactly this, entirely against the SQLite adapters from Checkpoint 4.
Once the full graph runs correctly end to end (happy path and reject-at-review-gate path) with
zero real external dependencies, move on to the frontend, real MCP servers, and — much later,
in Checkpoint 23c — the production Postgres/DynamoDB adapters, verified against the same
interface and behavior the SQLite adapters already proved out.
